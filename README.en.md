# APEXlang — Customers (demo project)

🌐 Also available in: [Português (Brasil)](README.md) | [Español](README.es.md)

## What this project is

A demo/test project exploring Oracle APEX application development using
**APEXlang** (a text-based DSL for APEX) together with **Claude Code** as
the AI agent, closing the loop with **SQLcl** and the **Oracle SQL
Developer extension for VS Code** (which imports/publishes the app
straight into the APEX workspace from the editor).

This is not a production project — it's a lab to validate the end-to-end
flow: describe a feature in natural language → the agent generates `.apx`
from grammar contracts and the real database schema → imports it into APEX
from VS Code → tests it in the browser → fixes whatever breaks → records
what was learned so the same mistake isn't repeated on the next page.

## What has been done so far

- Oracle APEX app `CUSTOMERS` created and published (workspace `ZONA`, app
  id `100`).
- Initial schema (`Database/DDL_v001.sql`): 5 tables — customers, phone
  types, sales representatives, customer phones, and orders — with
  `RAW(16)`/`SYS_GUID()` surrogate primary keys, trigger-maintained audit
  columns, foreign keys, and unique constraints.
- First feature requested via a natural-language prompt and implemented
  end to end: **Phone Types** maintenance — an Interactive Grid page
  (editing limited to Name/Description, Code is read-only, no inline
  insert/delete), record creation through a separate modal page, plus a
  menu entry and a breadcrumb entry.
- Project conventions and several real runtime issues hit along the way
  (with their root causes) documented in the `CLAUDE.md` files, so every
  new page starts out without repeating the same mistakes.

## How the repository is organized

```
APEXlang/
├── CLAUDE.md                        # repo-wide conventions for the AI agent
├── README.md / README.en.md / README.es.md
├── customers/                       # Oracle APEX app (app root — see below)
├── Database/                        # schema evolution (DDL) + data dictionary
└── Prompts/                         # per-app history of feature requests
```

### `customers/` — Oracle APEX app

Holds the `.apex`/`.apx` artifacts that the APEXlang skill generates and
that the Oracle SQL Developer extension imports/exports straight into the
APEX workspace. Unlike the skill's more common convention
(`applications/<app>/`), here `customers/` **is** the app root itself.

- `application.apx` — application definition (name, theme, authentication,
  navigation).
- `pages/` — one `.apx` file per page (`p00001-home.apx`,
  `p00002-phone-types.apx`, `p00003-phone-types-create.apx`, ...).
- `shared-components/` — breadcrumbs, navigation menu lists, authentication
  and authorization, theme, LOVs, static files.
- `supporting-objects/` — install/deinstall scripts for the app.
- `deployments/default.json` — target workspace and app id (`ZONA` /
  `100`).
- `apex-exports/` — automatic `.sql` backups the extension creates before
  every Import; this is a safety output, not a source of truth.

### `Database/` — schema and data dictionary

The authoritative source for the data model, fed by the Oracle JDeveloper
Database project.

- `DDL_vNNN.sql` — one file per version, generated by JDeveloper. **Each
  file is an incremental diff** (only what changed in that version), not a
  full schema snapshot — the current truth is the sum of every file applied
  in order.
- `Tables/<TABLE>.md` — a per-table data dictionary: field name (matching
  the actual database column), a display label in Portuguese, and a
  description. It complements the DDL with facts the DDL doesn't carry
  (label, description, hidden/non-editable hints) and is treated as
  authoritative metadata, on the same footing as the DDL — not as a loose
  comment.

### `Prompts/` — request history

One file per requested feature, never overwritten:
`Prompts/<app>/NNN_FeatureName.md`. Each file records the original request
and, when applicable, the problems found during implementation and how
they were fixed — effectively a living changelog per feature.

## Tools involved

- **Claude Code** with the `apexlang` skill, which generates and validates
  `.apx` from grammar contracts and real Oracle APEX compiler metadata
  (it doesn't "invent" syntax).
- **SQLcl** (`D:\Bin\sqlcl`) — used by the skill to query compiler metadata
  and by the VS Code extension to connect to the database.
- **Oracle SQL Developer extension for VS Code** — recognizes `.apx`/`.apex`
  files and publishes (Import) the app into the `ZONA` workspace straight
  from the editor.

## Conventions and details for anyone working on this project

The rules for how code is generated, how things are named (English for
technical scope/identifiers, Portuguese for anything the end user sees),
and the list of runtime pitfalls discovered along the way are documented
in:

- [`CLAUDE.md`](CLAUDE.md) — repository-wide conventions.
- [`customers/CLAUDE.md`](customers/CLAUDE.md) — conventions specific to
  the `CUSTOMERS` app.
